## 一、已有基础与实验记录

此前已经运行 xv6，并完成了以下观察：

| 实验 | 观察结果 | 对应认识 |
| --- | --- | --- |
| `pidtest` | 同一个进程两次调用 `getpid()`，都返回 `3` | 系统调用进入内核后，内核通过当前进程找到 PID |
| GDB 调试 | 观察到 `trapframe->a7` 中的系统调用号，以及 `trapframe->a0` 中的返回值 `3` | 请求编号与返回值通过不同寄存器传递 |
| `forkdemo` | 子进程 PID 为 `4`，`fork()` 返回 `0`；父进程 PID 为 `3`，`fork()` 返回 `4` | 同一次 `fork()`，父子进程得到不同返回值 |
| `memdemo` | 父子变量的虚拟地址相同，但值和物理页不同 | 不同进程可以拥有相同虚拟地址，并映射到各自的物理内存 |

一次 `memdemo` 的实际输出：

```text
[map] parent: va=0x0000000000001000, pa=0x0000000087f1f000
[map] child:  va=0x0000000000001000, pa=0x0000000087f28000
child: value=20, addr=0x0000000000001000
parent: value=10, addr=0x0000000000001000
```

这里是不同物理页上的独立副本。结合本地 `uvmcopy()` 的 `kalloc → memmove → mappages` 实现，可以看到已分配页面在 `fork()` 时被复制。不能仅凭父子变量值不同，就判断某个系统是否使用了写时复制。

PID 和物理地址是当次运行结果，重新运行时可能变化。

此前还梳理了以下流程：

```text
getpid()
  → 用户态系统调用汇编桩
  → ecall
  → uservec → usertrap → syscall → sys_getpid
  → 返回值写入 trapframe->a0
  → prepare_return → userret → sret
  → 回到用户态
```

- `a7` 保存系统调用编号，`a0` 用于返回结果。
- `trapframe` 保存用户态寄存器现场；`context` 保存内核执行切换所需的现场。
- `scheduler()` 选择可运行进程，`swtch()` 切换内核执行现场。
- `sleep()` 让进程等待事件；`wakeup()` 使其变为可运行，并不保证立即执行。
- `exit()` 使进程进入退出状态；`wait()` 等待并回收子进程。

## 二、exec：同一个进程换一个程序

### 1. fork 与 exec 的分工

- `fork()`：创建子进程。
- `exec()`：替换当前进程的用户程序，PID 保持不变。

Shell 执行普通命令时，基本结构是：

```c
if (fork() == 0) {
  exec("pidtest", argv);
  fprintf(2, "exec failed\n");
  exit(1);
}
wait(0);
```

父 Shell 等待子进程；子进程最初执行 Shell 代码，随后通过 `exec()` 换成目标程序。

### 2. 内核中的执行路径

```text
用户态 exec()
  → 系统调用入口
  → sys_exec()
  → kexec()
      → 找到可执行文件
      → 读取、检查 ELF
      → 创建新的用户页表
      → 分配内存，装入代码和数据
      → 建立用户栈，放入参数
      → 提交新的用户地址空间
      → 释放原来的用户地址空间
```

提交新程序时，关键状态发生变化：

```c
p->pagetable = pagetable;
p->trapframe->epc = elf.entry;
p->trapframe->sp = sp;
```

内核随后返回用户态时，会使用新页表、新栈和新的程序入口。

### 3. 为什么成功后不会执行 exec 后面的语句

成功时，用户态返回位置已经变为 ELF 中记录的新程序入口，因此不会继续执行原程序中 `exec()` 后面的错误处理代码。

失败时，例如文件不存在，原用户程序得以保留，`exec()` 返回 `-1`，调用者继续执行错误处理。

需要区分：内核函数 `kexec()` 正常返回，不代表成功的用户态 `exec()` 会返回原调用位置。本地实现中，`kexec()` 返回 `argc`，由系统调用分发代码写入新程序的 `a0`；`a1` 保存新程序的 `argv` 地址。

## 三、文件描述符：程序怎样找到输入输出对象

### 1. fd 是当前进程打开文件表的下标

每个进程维护：

```c
struct file *ofile[NOFILE];
```

读写的基本关系是：

```text
fd → 当前进程的 ofile[fd] → 内核打开文件对象 → 具体读写操作
```

文件描述符可以对应普通文件、控制台设备或管道。

| fd | 约定名称 | 通常用途 |
| --- | --- | --- |
| 0 | 标准输入 | 读取输入 |
| 1 | 标准输出 | 输出正常结果 |
| 2 | 标准错误 | 输出错误信息 |

这些编号的用途是约定，最终连接到什么对象，要看当前进程的文件描述符表。

### 2. 用户态 printf 到终端的路径

```text
printf()
  → vprintf(1, ...)
  → putc()，逐字符调用 write(1, ...)
  → 系统调用入口 → sys_write()
  → 查 ofile[1] → filewrite()
  → 控制台设备分支 → consolewrite()
  → uartwrite()
  → QEMU 终端显示字符
```

用户态 `printf()` 负责格式化，实际输出通过 `write()` 系统调用完成。

### 3. fork 与 exec 对描述符的影响

- `fork()` 后，父子进程各有自己的描述符表，但表项可以引用同一个内核文件对象。
- 复制引用时会增加引用计数；子进程关闭一个描述符，不会清除父进程的表项。
- `exec()` 保留文件描述符表，新程序沿用已经设置好的输入输出连接。

## 四、重定向：为什么输出可以写入文件

以这条命令为例：

```sh
echo hello > out
```

Shell 在子进程中先完成相当于下面的操作，再执行 `echo`：

```c
close(1);
open("out", O_WRONLY | O_CREATE | O_TRUNC);
exec("echo", argv);
```

正常情况下，`0、1、2` 原本已经打开。关闭 `1` 后，`open()` 选择最小空闲编号，得到新的 `fd 1`：

```text
原来：ofile[1] → 控制台
之后：ofile[1] → out 文件
```

打开标志分别表示：

- `O_WRONLY`：只写。
- `O_CREATE`：文件不存在时创建。
- `O_TRUNC`：已有普通文件的内容被清空。

`echo` 仍然调用 `write(1, ...)`，但内核这次把内容写入文件。父 Shell 的描述符表没有被一起修改。

补充：此前加入的 `[kernel] getpid returns ...` 来自内核 `printf()`，不经过用户进程的标准输出。它不会因为 `pidtest > out` 而一起被重定向。

## 五、管道：把两个进程的输入输出接起来

以这条命令为例：

```sh
echo hello | wc
```

数据流是：

```text
echo 的 fd 1
    → 内核管道缓冲区
    → wc 的 fd 0
    → wc 统计结果
    → wc 的 fd 1 → 终端
```

### 1. 创建管道

```c
int p[2];
pipe(p);
```

- `p[0]` 保存读端的文件描述符。
- `p[1]` 保存写端的文件描述符。
- 数组下标 `0、1` 不代表描述符编号固定为 `0、1`。
- 本地 xv6 的管道包含一个 512 字节的内存缓冲区。

### 2. 连接左右两侧命令

左侧进程执行目标程序前：

```c
close(1);
dup(p[1]);
close(p[0]);
close(p[1]);
```

右侧进程执行目标程序前：

```c
close(0);
dup(p[0]);
close(p[0]);
close(p[1]);
```

`dup()` 在最小空闲位置建立对同一个打开文件对象的引用。因此，左侧的 `fd 1` 接到写端，右侧的 `fd 0` 接到读端。

关闭原来的 `p[0]`、`p[1]` 后，保留下来的标准输入或标准输出仍然引用对应管道端。

### 3. 等待、唤醒与 EOF

| 状态 | 正常情况下的行为 |
| --- | --- |
| 管道有数据 | 读取当前可用数据 |
| 管道为空，仍有写端打开 | 读取进程睡眠，等待数据 |
| 管道为空，所有写端引用均已关闭 | `read()` 返回 `0`，表示 EOF |
| 管道已满，仍有读端打开 | 写入进程睡眠，等待读取腾出空间 |

写入数据后可以唤醒读取者；读取腾出空间后可以唤醒写入者。

EOF 是读取返回的状态，不是某个特殊字符。必须关闭所有多余的写端引用，否则读取者可能一直等待后续数据。

本地 Shell 的进程关系是：

```text
主 Shell
  └─ 执行管道命令的子进程
       ├─ 左侧命令：echo
       └─ 右侧命令：wc
```

中间的执行进程关闭自己持有的管道两端，并等待两个命令结束；随后主 Shell 回收它，继续读取下一条命令。
